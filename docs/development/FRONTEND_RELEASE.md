# Выпуск DIO Messenger Web

## Сборка и доставка

1. Дождаться зелёных проверок Messenger Frontend для выбранного SHA. Workflow собирает production PWA и запускает браузерные сценарии на Chromium, Firefox и WebKit.
2. Взять артефакт `messenger-web-<sha>`. Развернуть его на staging как набор статических файлов. Положить рядом `messenger-runtime.json` с публичными HTTPS-адресами или путями reverse proxy на том же origin. Для production использовать тот же артефакт и конфигурацию production. Конфигурация содержит публичные URL. Допустимые переменные и шаблон приведены в [примере runtime-конфигурации](../../messenger.web/config/messenger-runtime.example.json).
3. Настроить TLS, WSS, CORS и ограничения CSP на ingress. Доступ к REST, WebSocket и хранилищу подписанных ссылок проверить из браузера под адресом фронта. HTML и service worker должны перепроверяться при запросе. Для runtime-конфигурации требуется `Cache-Control: no-store`. Хэшированные файлы можно кешировать как immutable. [Пример конфигурации nginx](../../docker/frontend/nginx.conf)
4. После выкладки открыть `/release.json` и проверить SHA. Запустить live-сценарии из раздела ниже. Перед продвижением в production проверить откат на предыдущий артефакт. Сохранить доступность хэшированных файлов предыдущего релиза до окончания перехода пользователей. Проверить, что существующие черновики и outbox открываются в обеих версиях.

Service worker кеширует оболочку и статические ресурсы. В режиме runtime-конфигурации браузер хранит последнюю валидную конфигурацию для запуска без сети. Запросы API, runtime-конфигурация и подписанные ссылки не входят в кеш Workbox. Установка новой версии предлагает обновиться по действию пользователя.

## Проверка staging

Для ручного запуска workflow подготовить защищённое окружение `messenger-staging` в GitHub. Указать `PLAYWRIGHT_STAGING_URL`, `STAGING_MESSENGER_API_URL`, `STAGING_CHAT_ID`, `STAGING_CHAT_TITLE`, `STAGING_MEMBER_ID` и при необходимости `STAGING_MEMBER_ROLE` как variables. Логины и пароли владельца и второго участника задать как secrets `STAGING_OWNER_EMAIL`, `STAGING_OWNER_PASSWORD`, `STAGING_MEMBER_EMAIL`, `STAGING_MEMBER_PASSWORD`. Использовать выделенную тестовую беседу. Проверка отправляет сообщения с префиксом `[staging]` и проверяет снятие и восстановление членства второго участника.

Запуск с теми же переменными доступен через `pnpm e2e` из `messenger.web`. Сценарии загружают deployed PWA, проверяют доставку после офлайн-перезапуска, обновление сессии в двух вкладках и очистку после отзыва доступа. Отдельно пройти выдачу, истечение и отзыв доступа к ссылкам на медиа с аккаунтами сотрудника и гостя. Проверить мобильную клавиатуру, экранный диктор и управление фокусом на целевых устройствах.

Локальная матрица покрывает Chromium, Firefox и WebKit с тестовыми ответами API. Запуск установленной PWA без сети автоматизирован в Chromium. Для Firefox и WebKit этот сценарий входит в приёмку на целевых браузерах. Локальная проверка активации новой и предыдущей версии service worker подтвердила сохранение черновика. Полный откат релизного артефакта проверяется на staging.

## Условия допуска

| Проверка | Условие |
|---|---|
| Сохранность переписки | Проверки CI зелёные, live-приёмка подтверждает доставку ровно одного сообщения, восстановление истории и очистку после отзыва доступа. |
| Сессия | Закрыть решение по HttpOnly refresh-cookie с DIO Desk/IAM и проверить жизненный цикл сессии по HTTPS на staging. Текущий legacy-адаптер хранит refresh-токен в браузерном `localStorage`. При выходе локальное состояние сессии очищается во всех вкладках. Содержимое IndexedDB остаётся в хранилище аккаунта для восстановления черновиков после повторного входа. Политику очистки при выходе на общих устройствах нужно согласовать до выпуска. |
| Обновление и откат | Предыдущая и новая версии читают данные IndexedDB. После смены версии сохранены черновики и очередь. HTTPS и WebSocket доступны на обоих релизах. |
| Наблюдаемость и нагрузка | В production включён разрешённый сборщик через поле `telemetry` runtime-конфигурации или `VITE_TELEMETRY_URL`. Клиент отправляет код события, идентификатор сборки и выборочные замеры времени ACK и синхронизации. На staging измерены p95 ACK, доставки и восстановления связи на реалистичной истории по [плану проверок](TEST_PLAN.md). |

Детальный SLA DIO Desk, поиск по префиксу номера заявки, содержимое вложений заявки и индивидуальное время прочтения остаются контрактными задачами. Если они входят в первый релиз, проверить их отдельно перед выкладкой.
